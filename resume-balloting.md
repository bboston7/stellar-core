# Resume balloting on tx-set arrival (config-gated)

## Context

With parallel tx-set downloading, a node processes SCP envelopes up to the "vote to commit" gate without the tx set, then **blocks** at that gate (`BallotProtocol::setConfirmPrepared`, the `kStructurallyValidValue` branch, BallotProtocol.cpp:1170). Measurement (`scp.timing.txset-to-unblock-lag` — a temporary instrument, removed again before landing; a branch copy retains it) showed ~1s of *post-arrival* dead time: the node has the tx set in hand but doesn't commit until the 1s ballot timer fires, because nothing re-pokes balloting when the tx set lands.

This is the **third and preferred** option we explored (see `abandon-after-arrival.md` for the second). Instead of bumping the ballot to re-trigger evaluation, we directly **resume the deferred commit** at the same ballot. Two decisive advantages over the bump:

1. **Lag → 0, purely local.** When the node stalled it had *already raised `mHighBallot`* (BallotProtocol.cpp:1155-1158 runs before the commit gate) — i.e. it already confirmed-prepared `newH` with quorum support. The only skipped step was `mCommit = makeBallot(newC)` (1203). So committing at counter **N** uses ratification the node already holds — no new peer messages, no waiting for a quorum to follow a bump.
2. **No counter inflation.** Committing at N (vs bumping to N+1) leaves the network's ballot-counter dynamics untouched.

Committing at N is *more* correct, not less — it's exactly the protocol step that was deferred. The bump was only ever a workaround to re-trigger evaluation (needed because `attemptConfirmPrepared` short-circuits once `mHighBallot` is raised, BallotProtocol.cpp:1044-1048).

## Key finding: the tx-set arrival leaves a vacuum (verified this session)

Concern with the bump design was that the arrival's own processing might race the resume. It doesn't. On tx-set arrival, `addTxSet` → `mTxSetFetcher.recv` re-delivers the waiting envelopes (ItemFetcher.cpp:235-238), but they are **discarded before reaching the SCP FSM**, at two layers:

- `PendingEnvelopes::recvSCPEnvelope`: a released-early envelope was added to `mProcessedEnvelopes` (PendingEnvelopes.cpp:527). On re-delivery the `processed` check (496) returns **`ENVELOPE_STATUS_PROCESSED`** (506) without calling `envelopeReady`.
- `HerderImpl::recvSCPEnvelope`: only drives SCP (`processSCPQueue`) on **`ENVELOPE_STATUS_READY`** (922-933); `PROCESSED` just logs.

So `addTxSet` never invokes `advanceSlot` for the stalled envelope — which is *precisely why the lag exists*, and also why our resume operates in a vacuum: nothing else touches ballot state on arrival (`onTxSetReceived` only updates wrappers, HerderSCPDriver.cpp:1813-1843). **Consequence:** the stall flag survives `addTxSet`, and `receivedTxSet` can be called right after it with no special sequencing.

## The inverted safety model (the heart of this design)

Do **not** make correctness depend on clearing the stash on every SCP-state mutation — that's fragile cache-invalidation in consensus code, and a single missed path means committing a stale ballot (a fork). Instead, treat the stash as a mere *hint* and **verify live state before acting**. A missed/stale stash can then only cause a no-op, never a wrong commit.

**As built:** the stall stashes the deferred ballots **and the self statement the node emitted at the stall** — `std::optional<StalledCommit> mStalledCommit` holding `{mCommitBallot=newC, mHighBallot=newH, mStallStatement=<the emitted PREPARE(h, nC=0)>}`. All stash management lives at the **end** of `setConfirmPrepared`, keyed on `(didWork, stalledThisCall)`:

| `didWork` | `stalledThisCall` | action |
|---|---|---|
| ✓ | ✓ | arm `{newC, newH, emitted}` — constructed whole from the emit's return value, never partially initialized |
| ✓ | ✗ | reset — the call advanced state (recorded a commit / raised h / bumped b) without deferring one, so any prior stash is superseded (and guard-dead against the fresh emission anyway) |
| ✗ | — | untouched — nothing was emitted, so the self statement is unchanged and a previously armed stash is exactly as valid as before; no-op calls (e.g. an incompatible ratified `newH` below the current ballot) don't destroy a still-live stash |

The only `!didWork` path through the stall branch is `receivedTxSet`'s own re-evaluation (it calls with `newH == mHighBallot`, so nothing raises), and `receivedTxSet` consumes the stash before calling — so a *failed* resume leaves resume disarmed rather than re-armed (see the re-stall subsection below).

`receivedTxSet(Value const& v)`:
1. `if (!mStalledCommit || mStalledCommit->mCommitBallot.value != v) return;` then consume the stash.
2. Verify the node has done **no balloting work since the stall**: its own latest statement, `mLatestEnvelopes[localNodeID]->getStatement()`, is byte-identical to `stalled.mStallStatement`. This one equality check subsumes phase, `mCommit`, `mHighBallot`, `mPrepared`, `mPreparedPrime`, and `mCurrentBallot` — every field is encoded in the PREPARE statement. Any divergence → no-op; the normal path / ballot timer handles it.
3. Re-invoke `setConfirmPrepared(stalled.mCommitBallot, stalled.mHighBallot)`. With the tx set now available, `validateValue` returns `kFullyValidatedValue`, so it sets `mCommit`, and `emitCurrentStateStatement()` self-processes (`Slot::processEnvelope(self)`) and continues the FSM (accept/confirm commit) exactly as the normal path would.

**Re-stall = disarm (the failed-resume case).** The resume's re-invocation can still see `kStructurallyValidValue` for a real reason: `validateValueHelper` maps an **arrived-but-invalid** tx set (fails `checkAndCacheTxSetValid`) to `kStructurallyValidValue` too (HerderSCPDriver.cpp:507-514, under `protocolAllowsEmptyTxSetValues`). In that case `setConfirmPrepared` re-stalls with `didWork == false`, and — per the matrix — does **not** re-arm the consumed stash. That is the semantically right outcome: the arrival already happened, so there is no future arrival event to resume on; recovery belongs to the ballot timer, whose bump runs `maybeReplaceValueWithEmptyTxSet` (BallotProtocol.cpp:402) and swaps in the empty-tx-set value **immediately** when the tx set is present-but-invalid (no waiting time → replace now), or after `getTxSetDownloadTimeout()` while still downloading. (History: an earlier version armed the stash in the stall *branch* with an empty placeholder statement and filled it in post-emit only when `didWork` — so this re-stall re-armed a stash whose empty statement could never match, a state that was only harmless by accident. The matrix removes the partially-constructed state entirely.)

**Why reuse `setConfirmPrepared` instead of re-deriving `newC`** (the originally-planned `findCommitBallot` extraction): re-calling the tested function with the stored `(newC, newH)` means **no new commit-derivation code** in the heart of the ballot protocol. And "self statement unchanged" guarantees the entire ballot state still matches the stall, so the re-run reproduces exactly the deferred step — the h-raise is a no-op and `c ≤ h` still holds. This is the "no work since the stall" form of the inverted safety model, and comparing one statement is **complete by construction**: it can't be defeated by a state field or a mutator we forgot. (An earlier field-by-field version *did* forget one — `mPrepared`/`mPreparedPrime`, which gate commit-safety in the bypassed `attemptConfirmPrepared`; the statement check covers them for free, since `p`/`p'` are in the statement.)

## Driving `setConfirmPrepared` outside `advanceSlot` (two subtleties, both benign)

Normally `setConfirmPrepared` is reached only via `advanceSlot → attemptConfirmPrepared`. `receivedTxSet` calls it directly — it must, because `attemptConfirmPrepared` short-circuits once `mHighBallot` is raised, so routing through `advanceSlot` would never reach the commit step. Two things `advanceSlot` normally provides need accounting for; both hold up.

**1. The downstream FSM still runs — via the self-emit, with the self statement as the hint.** Setting `mCommit` isn't the end of it: the normal path also runs `attemptAcceptCommit`/`attemptConfirmCommit`/`attemptBump`/`checkHeardFromQuorum` afterward. Those still run here, because `setConfirmPrepared` → `emitCurrentStateStatement` → `Slot::processEnvelope(self)` → `advanceSlot(selfStatement)` (BallotProtocol.cpp:274-275) — the *same* self-emit re-entry the normal path uses (there, as a nested level-2 call). The only difference is the `hint` is the node's own statement rather than an enclosing peer statement. That's benign: the hint is a search *focus*, not a correctness input (the `attempt*` methods scan all of `mLatestEnvelopes`), and the self statement's working ballot is exactly the value being committed, so commit progression for that value is evaluated correctly. Any peer-hint-driven progress either already happened when that peer statement arrived, or happens on the next one. Worst case is a one-statement-delayed commit *acceptance*, which self-heals; agreement is untouched (we only complete a step the node already earned).

**2. `sendLatestEnvelope` fires at level 0 here (not a no-op) — and that's correct.** `sendLatestEnvelope` only emits when `mCurrentMessageLevel == 0`, and dedups against `mLastEnvelopeEmit` (BallotProtocol.cpp:2234-2240); the consolidated send normally happens at the outermost `advanceSlot`'s unwind (`if (didWork) sendLatestEnvelope();`, 2157-2160). On the resume path we start at level 0, so the `emitCurrentStateStatement` send (line 747) is live rather than a no-op. Tracing both shapes: if the resume **cascades** (accept-commit → CONFIRM/EXTERNALIZE), the `advanceSlot(self)` it triggered does the consolidated send at *its* level-0 exit, and line 747 then no-ops (its `isNewerStatement` guard sees the newer cascade envelope, and `mLastEnvelopeEmit` dedups); if it **doesn't cascade**, line 747 sends the single `PREPARE(c=N)` once. Either way: one broadcast of the latest envelope, deduped, cascades still consolidated. And this level-0 entry is **not novel** — `ballotProtocolTimerExpired → abandonBallot → bumpState → emitCurrentStateStatement` (BallotProtocol.cpp:610-614) already emits and sends from level 0 the same way. The `mCurrentMessageLevel == 0` gate and `mLastEnvelopeEmit` dedup exist precisely for these level-0 entry points.

## ⚠️ Prototype-unsafe: the `isNewerStatement` change (must revisit before productionizing)

Implementation surfaced a structural conflict the design missed, and the current fix is **deliberately not known to be safe** — acceptable only because this is a prototype to measure whether the approach is worth pursuing.

**The conflict.** SCP's PREPARE total order (`BallotProtocol::isNewerStatement`, the PREPARE branch) is `(b, p, p', nH)` and deliberately **excludes `nC`** — in the unmodified protocol a node sets `h` and `c` together, so `c` never changes while `(b, p, p', h)` stay fixed. This feature breaks that assumption: the commit gate emits `PREPARE(h.n=N, c.n=0)` while the tx set downloads, then the resume re-emits the **same ballot** with `c.n=N`. Those differ only in `nC`, so `isNewerStatement` judged the resume statement *not newer* → `processEnvelope(self)` dropped it as stale → `emitCurrentStateStatement` threw `"moved to a bad state"`. (The pre-existing timer-bump unblock never hit this because bumping advances `b`, which *is* in the order.)

**The prototype fix (chosen).** Widen the PREPARE order to tiebreak on `nC` when `nH` is equal: `(b, p, p', nH, nC)`. This makes the same-ballot commit statement broadcastable, preserving the no-counter-bump benefit. The widening is **protocol-gated** on `protocolAllowsEmptyTxSetValues()` (node's LCL version ≥ `EMPTY_TX_SET_PROTOCOL_VERSION`, read via the driver — which is why the ordering function is now a member, not static): gate off reproduces the upstream `(b, p, p', nH)` order byte-for-byte (the else-branch `nH <` compare is false on equality), and all in-sync validators flip together at the upgrade ledger close.

**What the protocol gate resolves — the coordination/divergence half.**
- Gate off ⇒ no stall can exist (`kStructurallyValidValue` implies the protocol allows empty tx sets — releaseAsserted at the commit gate) ⇒ no resume ⇒ no honest node ever emits two PREPAREs differing only in `nC`. The tiebreak is active **exactly when the phenomenon it orders can exist**. Note that a per-node config flag could never provide this (it isn't network-uniform); the protocol version is the right key. (Consistently, the feature has no config flag of its own — see the Config section below.)
- The widening is a **pure refinement** of the old order: every pair the old order ranks, the new order ranks identically — it only *adds* orderings for `nH`-equal/`nC`-differing pairs the old order called "not newer". So flipping the gate can never invert an existing comparison, state recorded pre-flip stays valid post-flip, and even a *mixed* population degrades gracefully rather than diverging: a gate-off node treats a resume statement exactly as today's network would (drops it as stale, keeps the `c=0` one) and catches up when the node's next CONFIRM supersedes it by statement type. Mixed-ness costs the feature's benefit, not correctness — and the gate keeps the voting set from running mixed at all.

**Why this is still risky / open for productionization.**
- The **semantic widening itself is unvetted** — the gate settles *who* uses the order, not whether the order is right. Post-upgrade, the split confirm-prepared/vote-commit step becomes observable network-wide (peers legitimately see h-then-c as two statements at the same ballot); every consumer of PREPARE statements should be audited for "same `(b,p,p',nH)` ⇒ same statement" assumptions. In its favor (intuition, not proof): honest `nC` is monotone at fixed `(b,p,p',nH)` and `isStatementSane` bounds `nC ≤ nH ≤ b.counter` (BallotProtocol.cpp:141-142), so per-node statement sequences still only ever *add* votes — no retraction is expressible.
- **Boundary skew / time-dependence — inherent to protocol gating, not a new concern.** The gate reads the node's *own* LCL, so a lagging node runs the old order until it catches up (dropping/not forwarding resume statements — benign: it isn't voting, and refinement means nothing it recorded becomes wrong), and the comparator's answer for the same two statements can change across the upgrade boundary. These are the same per-node-LCL flip semantics as *every* protocol-versioned behavior in core, and this subsystem already leans on them harder: `validateValue` (which gates envelope acceptance, upstream of ordering) is LCL-dependent throughout, and `maybeReplaceValueWithEmptyTxSet` changes the *value a node votes for* based on LCL plus per-node download clocks. Doing better is informationally impossible — a node behind the upgrade ledger cannot know the upgrade activated until it catches up, so its LCL *is* its best knowledge of the network's protocol version. Perfect behavior for in-sync validators (atomic flip per ledger-cohort) is the achievable bar, and it's met. **The one discipline to preserve:** future edits to the gated branch must stay *refinement-only* (widen the order, never alter existing rankings) — the safe-across-the-boundary reasoning depends on it.
- **Byzantine churn, bounded:** gate on, a malicious node can walk `nC` upward step-by-step at a fixed ballot, each step "newer" → recorded and re-flooded. Bounded by the `nC ≤ nH ≤ b.counter` sanity check, and counter bumps already offer cheaper amplification — no meaningful new surface.
- **Alternatives if we productionize:** (a) suppress the stall's `h`-only emission so `nH` advances at resume (`0→N`) and the statement is newer under the *unchanged* order — plausibly liveness-neutral but creates an internal-vs-recorded-state divergence during the stall that needs its own analysis; (b) fall back to the bump (`abandon-after-arrival.md`), which is SCP-idiomatic for broadcasting a new vote but costs a counter and quorum-follow latency.

## Changes by file

### 1. `src/scp/BallotProtocol.{h,cpp}` — stall stash, resume, statement-order tiebreak
- Add a `struct StalledCommit { SCPBallot mCommitBallot; SCPBallot mHighBallot; SCPStatement mStallStatement; };` and member `std::optional<StalledCommit> mStalledCommit;`.
- Make `emitCurrentStateStatement()` **return the `SCPStatement` it generated** (built from current state, *before* its `processEnvelope(self)` recursion). Callers that ignore the return are unaffected.
- In the blocked branch (`setConfirmPrepared`, `kStructurallyValidValue`, alongside `recordBallotBlockedOnTxSet`): only set a local `stalledThisCall` flag — the branch itself never touches `mStalledCommit`. All stash management happens once, at the end of the function, per the `(didWork, stalledThisCall)` matrix in the safety-model section: arm whole on stall-with-work, reset on work-without-stall (subsumes the old commit-branch reset), untouched on no work. `mStallStatement` comes from the **return value** of `emitCurrentStateStatement()` — *not* `mLatestEnvelopes[self]`. The emit's recursion can advance the ballot and record a *newer* self statement; capturing that instead of the generated `PREPARE(h, nC=0)` would let a resume proceed on an advanced state — re-opening the `mPrepared` gap, or asserting `!mCommit` if the recursion reached CONFIRM. Capturing the generated statement makes the guard decline whenever the recursion (or anything later) moved state.
- Add `void receivedTxSet(Value const& v)`: match value, consume the stash, then resume only if `getLatestMessage(localNodeID)->statement == stalled.mStallStatement` (`xdr::operator==`, already used at BallotProtocol.cpp:735); it **re-invokes `setConfirmPrepared(storedC, storedH)`** rather than re-deriving `newC`.
- **`isNewerStatement` PREPARE branch:** add the `nC` tiebreak when `nH` is equal, gated on `protocolAllowsEmptyTxSetValues()`. Reading the driver made the two-statement overload a member instead of static (`Slot::isNewerNominationOrBallotSt` now calls it via `mBallotProtocol`). See the ⚠️ section above — this is the load-bearing prototype-unsafe change.

### 2. `src/scp/Slot.{h,cpp}` and `src/scp/SCP.{h,cpp}` — forwarders
- `Slot::receivedTxSet(Value const& v)` → `mBallotProtocol.receivedTxSet(v)` (mirror the public `Slot::abandonBallot()`, Slot.cpp:214).
- `SCP::receivedTxSet(uint64 slotIndex, Value const& v)` (new public method) → `getSlot(slotIndex, false)` (protected, SCP.h:179), null-guard, then `slot->receivedTxSet(v)`. SCP stays value-opaque — no `StellarValue`/`txSetHash` knowledge here.

### 3. `src/herder/HerderSCPDriver.{h,cpp}` (+ `PendingEnvelopes`) — arrival plumbing
- Track stalling `(slot, value)` by tx set hash: a member `UnorderedMap<Hash, std::vector<std::pair<uint64_t, Value>>> mStallingByTxSet;` (Value → txSetHash via `xdr_from_opaque`, as in `measureAndRecordBallotBlockedOnTxSet`, HerderSCPDriver.cpp:1361). Populate in `recordBallotBlockedOnTxSet`; drop the entry in `measureAndRecordBallotBlockedOnTxSet` (unblock). (Same shape as the bump plan's tracking; correctness doesn't hinge on it being perfectly pruned, thanks to the verify at resume.)
- **Bounded lifetime:** `HerderSCPDriver::purgeSlotsOutsideRange` also sweeps `mStallingByTxSet`, dropping entries whose slot falls outside the retained range (honoring `slotToKeep`, like the `mSCPExecutionTimes` sweep next to it). Without this, an entry whose tx set never arrives — the slot externalized a *different* value and the fetch was abandoned at ledger close — would live until process restart, since all steady-state pruning is keyed on the tx set arriving (`maybeResumeBalloting` / `measureAndRecordBallotBlockedOnTxSet`). This gives the map the same lifetime it would have had if it lived inside `Slot`.
- New `maybeResumeBalloting(Hash const& txSetHash)`: gated on `isParallelTxSetDownloadEnabled()` (as is the `mStallingByTxSet` insertion in `recordBallotBlockedOnTxSet` — the gate can only move false→true, so no entry is ever stranded by a flip); for each `(slot, value)` stalling on this hash, call `mSCP.receivedTxSet(slot, value)` **synchronously** — no `postOnMainThread`. Deferral is unnecessary: the SCP FSM is never on the stack during a tx-set arrival (`recvTxSet` is overlay-top-level, never nested in `advanceSlot`; the re-feed is inert per the dedup finding, so nothing drives the FSM before this call), making it a clean top-level entry — the same way `HerderImpl::recvSCPEnvelope` drives `processSCPQueue` synchronously. SCP's only reach into overlay is outbound broadcast (`emitEnvelope`), which doesn't cycle back into the inbound tx-set path, and any self-processing recursion is inherent to the normal `setConfirmPrepared` path (bounded by `MAX_ADVANCE_SLOT_RECURSION`). Synchronous is also lower-latency (no extra main-thread hop) — which is the whole point.
  - **Iterate a snapshot** of the stalling entries (copy/`std::move` the hash's vector out before the loop): a successful `receivedTxSet` calls `measureAndRecordBallotBlockedOnTxSet`, which prunes `mStallingByTxSet`, so iterating it live would mutate-under-iteration.
- Call `maybeResumeBalloting(hash)` from the arrival path after `addTxSet` (the tx set is in cache by then, so re-validation passes) — e.g. at the end of `onTxSetReceived`.

### 4. `src/main/Config.{h,cpp}` — no flag of its own
- The feature originally had a dedicated `EXPERIMENTAL_RESUME_BALLOTING_ON_TXSET_ARRIVAL` flag (useful for the initial A/B sims); it was removed before landing. Resume is gated on `isParallelTxSetDownloadEnabled()` (`EXPERIMENTAL_PARALLEL_TX_SET_DOWNLOAD` && the protocol allowing empty tx set values) — it ships as part of parallel downloading. Tradeoff accepted: there is no longer a lever to run parallel download *without* resume, so any future isolation A/B is branch-vs-branch.

## Why the resume logic is safe — with one explicit exception
- **Resume only if no work since the stall** — the node's own latest statement must be byte-identical to the stall statement. One equality check covers all of `b, p, p', c, h` + phase, so a moved or stale state can only no-op, never mis-commit — and it can't miss a field, unlike a hand-picked check.
- **Commits at the already-confirmed ballot** — uses banked quorum ratification; no new SCP agreement is fabricated.
- **The arrival is a vacuum** (dedup finding above) — the resume races nothing; the stash survives `addTxSet`.
- **Fallback intact:** if the tx set never arrives, the 5s `TX_SET_DOWNLOAD_TIMEOUT` → `abandonBallot` → empty-tx-set path still fires. This purely adds a fast path.
- **Exception:** the `isNewerStatement` widening (⚠️ section) is *not* covered by this reasoning — the protocol gate settles who runs it and when, but the widening's semantics remain the one deliberately-unvetted change and the thing to revisit before productionizing.

2. **Unit test (implemented, deterministic):** added to `SCPTests.cpp` on the existing `"setConfirmPrepared stalls on kStructurallyValidValue value"` case — a `TestSCP::receivedTxSet` wrapper plus three sections: resume commits at the **same counter** (`nC==1, nH==1`) with no bump/new-envelope; no-op on a non-matching value; and stays stalled when the tx set is still absent. (This test is what caught the `isNewerStatement` conflict: the resume emission threw until the `nC` tiebreak was added.)
   - **Stale-stash regression sections (implemented):** two more sections verify the statement guard *declines* when balloting moved between stall and arrival — (a) a local ballot bump (the timer-fires-just-before-arrival race), and (b) a higher **incompatible** prepared ballot accepted via quorum vote + v-blocking counter bump, with `phase`/`mCommit`/`mHighBallot` all deliberately unchanged. Both are states a field-by-field guard on those three would have resumed on; (b) is the shape that would bypass the p/p′ commit gate. Section (a) also confirms the normal path still completes after a declined resume.
   - **Stash-lifecycle pins (implemented):** the resume-success section asserts a repeat `receivedTxSet` no-ops (commit → reset); the still-absent section asserts that after a failed resume, even a genuine later arrival does **not** resume (failed resume = disarm; the timer owns recovery). These pin the `(didWork, stalledThisCall)` matrix semantics rather than catch the old empty-statement bug, which was observably identical through the public API (it also declined — just via a stash that could never match).
3. **Sim A/B (run before the dedicated flag was removed — resume off vs on, parallel download on in both):** `scp.timing.txset-to-unblock-lag` collapses with resume on; the `scp.timing.total` regression vs baseline disappears (parallel download realizing its head-start — confirmed to parity on a sparse topology; the denser-topology run was also completed). Ballot-counter-at-externalize stays flat (unlike the bump approach). Future isolation A/Bs are branch-vs-branch, since resume now ships with parallel downloading. The `txset-to-unblock-lag` metric was removed after these runs (a branch copy retains it); the surviving signals are `ballot-blocked-on-txset` — which largely subsumes it, since with resume on the blocked duration ≈ pure download wait — and `scp.timing.total`.

## Tradeoff vs `abandon-after-arrival.md`
- **This (resume):** eliminates the lag (local commit at N), no counter inflation, cleanly unit-testable — at the cost of new consensus-critical code (the resume path + a small refactor of the commit branch). Safe *if* the inverted safety model is adopted.
- **Bump (`abandonBallot`):** reuses a fully-tested path (near-zero new SCP logic), but only *reduces* the lag (quorum must follow the bump to N+1) and nudges counters up by one. 
- **Recommendation:** pursue this one; keep the bump as the low-risk fallback if the resume refactor proves gnarlier than expected.
